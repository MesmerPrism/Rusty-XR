Makepad Strategy

Makepad is the app shell. Rusty XR keeps the camera contracts.

Rusty XR uses Makepad where Rust-native UI, panels, live iteration, and headset diagnostics need a strong framework. Raw camera resources, projection timing, frame freshness, and validation contracts stay explicit and framework-neutral.

  • Rust-native UI
  • XR panels
  • Camera lane contracts
  • Upstream alignment
  • External texture metadata
  • Upstreamable diagnostics
Use

Makepad is a promising Rust UI, app-shell, and XR-panel substrate for controls, inspectors, and diagnostic tools.

Keep

Rusty XR keeps frame identity, resource identity, transforms, color status, lifecycle, and validation evidence as public contracts.

Contribute

Generic external-resource metadata, video lifecycle events, Android lifecycle hooks, and shader-resource diagnostics can become Makepad-level improvements.

Current Alignment

The maintained Makepad branch has started converging back toward upstream Makepad instead of remaining an isolated renderer experiment. Recent work integrated upstream video lifecycle, Android rendering, text wrapping, Android lifecycle, manifest/tooling, minimum-SDK, and Android App Bundle packaging directions while preserving Rusty XR camera-lane diagnostics.

What Makepad Provides

Makepad is a Rust-native application stack: a custom GPU-first UI/runtime framework, widget layer, Studio tooling, live design language, and cross-platform build tooling. Current public materials frame Makepad 2.0 around AI-native Rust UIs and Splash, while the repository and book describe a broader Rust-first framework for native, mobile, and web targets.

SurfaceRusty XR Reading
Widgets and panelsGood fit for XR controls, diagnostics, operator panels, graph views, and settings.
GPU text and vector UIUseful for crisp headset panels without routing all UI through a low-resolution canvas texture.
Live/Splash-style UIPromising for faster diagnostic and operator-tool iteration once the runtime contracts are stable.
Platform toolingUseful for Android and mobile workflows, but still needs explicit validation around Quest/XR camera paths.
XR rootsHistorically relevant and useful, but not a replacement for raw camera-resource contracts.

Why Rusty XR Uses It

  • Rust-native UI and app structure.
  • High-quality 2D panels inside XR scenes.
  • Room for live UI and tooling iteration.
  • A serious upstream project with real app pressure from Studio, Robrix, Moly, and related work.
  • A framework lane for comparing direct HWB/OES renderers against a Makepad-first app shell.

What Stays Explicit

  • Camera frame identity and timestamps.
  • Hardware-buffer, OES, and CPU-YUV transport identity.
  • Acquire, upload/import, reuse, stale, and release lifecycle facts.
  • Camera crop, transform, projection, color, and stereo lane semantics.
  • XR frame timing, submission evidence, and validation summaries.

Adapter Direction

Shared camera texture lane contract
  -> Direct Vulkan/HWB adapter
  -> Direct OpenGL/OES adapter
  -> Makepad CPU-YUV adapter
  -> Makepad hardware-buffer/external-texture adapter

The Makepad adapters should translate Makepad events and resources into the same Rusty XR contract used by the direct renderers. Rusty XR core crates stay independent of Makepad.
